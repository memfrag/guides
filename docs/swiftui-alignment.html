SwiftUI Layout Field Guide

Alignment is a
line to live by

Every SwiftUI container asks its children the same question: “where is your .top? your .center? your baseline?” Each view answers with a number, and the container draws one dashed line and makes every answer land on it. That's the whole system — this page builds it up from that one idea, ending with a real bug it explains.

Click an alignment. The dashed line is the guide; the boxes are views of different heights being asked to meet it.

ViewDimensions → CGFloat

A guide is just a number

For every alignment, every view has a guide: a function that takes the view's own size and returns a distance from its edge. The defaults are exactly what you'd guess — and they're the values you're overriding when you reach for .alignmentGuide later.

guidedefault answer
.top / .leading0
VerticalAlignment.centerheight / 2
.bottom / .trailingheight / width
.firstTextBaseline (text)baseline of the first line
.firstTextBaseline (no text!)the bottom edge — remember this one
HStack · VStack · ZStack · frame

Who asks which question

A container only asks about the axis it doesn't already control. An HStack places children horizontally itself, so the only freedom left is vertical — its alignment: parameter is a VerticalAlignment. A VStack is the mirror image. ZStack, .frame(alignment:), .overlay and .background control neither axis, so they take a composite Alignment — one horizontal and one vertical guide, like .topLeading.

Rule of thumb Alignment never moves a container's frame — it distributes children inside whatever space the container was given. If a whole stack sits in the wrong place, the fix is spacing or frames, not alignment.
.frame(width:height:alignment:)

Frames: a container of one

.frame doesn't resize its child — it wraps the child in a new, invisible view of the requested size. When that wrapper ends up bigger than the content, it's a container with exactly one child, and its alignment: parameter answers the usual question: where inside me does the child sit? The default is .center, on both axes. 

Text("Done")
    // a row that spans the container, with the text pinned leading —
    // the everyday “make this whole row tappable / left-aligned” move
    .frame(maxWidth: .infinity, alignment: .leading)

Two consequences people trip on:

Alignment needs spare space. .frame(alignment: .leading) with no width does nothing — an unconstrained frame hugs its child, and there's no room left to distribute. If an alignment: seems dead, check that the frame is actually bigger than the content on that axis.

Alignment acts per axis. .frame(maxWidth: .infinity, alignment: .bottomTrailing) only moves the child trailing — with no height constraint there is no vertical slack, so the bottom half is inert. A composite alignment is just two independent guides.

Same machinery, one child .overlay(alignment:), .background(alignment:) and ZStack(alignment:) follow identical rules — a secondary view is placed inside (or behind) a host by joining guide pairs. Everything from the .alignmentGuide section below works there too.
Spacer · .offset · GeometryReader

Where alignment isn't

Half of alignment debugging is recognizing the tools that look like alignment but play by different rules.

Spacer competes; alignment negotiates

HStack { Text("Done"); Spacer() } and Text("Done").frame(maxWidth: .infinity, alignment: .leading) often render identically — but a Spacer is a real sibling that claims the leftover space as its own size, while frame alignment distributes spare room without adding a participant. Prefer the frame for pinning one view to an edge; reach for Spacer when you're distributing several views (Text; Spacer(); Button) or need its minLength to guarantee a gap. And mind that a bare Spacer() has a default minimum length — in tight layouts that minimum can win over your content's space.

offset and position move pixels, not layout

Alignment is a layout-time negotiation — move a view with a guide and its container's size, its siblings, and hit-testing all account for the new place. .offset shifts only the rendering after layout is done: the view still occupies its original slot, neighbors don't react, and it can happily draw over them. .position goes further and discards the parent's layout entirely, centering the view at a coordinate. Use .offset for decorative nudges and animation; the moment other views should respond to the movement, it's an alignment job.

Containers that never ask

Two containers have no alignment: parameter at all, and both are notorious:

GeometryReader is greedy (takes all proposed space) and pins its content top-leading — not centered like nearly everything else. Wrap the content in .frame(maxWidth: .infinity, maxHeight: .infinity) to get centering back.

ScrollView sizes its content to the content's ideal size, so a narrow child sits at the scroll origin rather than centering in the viewport. Give the content .frame(maxWidth: .infinity) to claim the viewport's width, and use .defaultScrollAnchor(.center) when you want the initial scroll position — a different thing from alignment — to start centered.

.multilineTextAlignment

Text, horizontally: three tools, three jobs

“Why won't my text center?” is the most-asked alignment question in SwiftUI, because three different tools all sound like the answer — and each aligns a different thing:

toolaligns what
VStack(alignment:) etc.the Text view among its siblings
.frame(maxWidth:alignment:)the text block within the frame's spare width
.multilineTextAlignmentthe wrapped lines inside the text block itself

The one that surprises everyone: .multilineTextAlignment never moves the text block. A Text hugs its content, so on a single short line the block is exactly as wide as the words and there is nothing to re-arrange — the modifier appears to do nothing. It only becomes visible once the text wraps and lines have different lengths. 

// A fully centered paragraph needs BOTH tools:
Text(longMessage)
    .multilineTextAlignment(.center)              // lines, within the block
    .frame(maxWidth: .infinity)                    // block, within the row
                                                   // (.center is the default)
Debugging recipe Text not aligning? Add .border(.red) to the Text. If the border hugs the words, the block itself needs placing — reach for .frame or the stack's alignment:. If the border spans the width you expected, the lines need arranging — reach for .multilineTextAlignment.
leading ≠ left

Leading is not left

SwiftUI's horizontal guides are deliberately not named .left and .right. .leading means where reading starts — the left in English, the right in Arabic or Hebrew. Every leading/trailing guide, stack alignment, frame alignment, and TextAlignment resolves against the environment's layoutDirection, so a layout written once mirrors correctly for free. 

// Audit any screen's mirrored layout without changing your locale:
ContentView()
    .environment(\.layoutDirection, .rightToLeft)
What doesn't flip Alignment mirrors automatically; content doesn't always. SF Symbols with a natural direction provide RTL variants, but your own directional images may need explicit handling, and things that are physically sided — a slider tracking a real-world dial, musical notation — should sometimes stay LTR. Mirroring layout is free; deciding what deserves mirroring is design.
.firstTextBaseline / .lastTextBaseline

Baselines: the typographer's guide

Centering a label against a taller control looks fine until the text wraps or the control grows. Aligning baselines — the invisible line type sits on — keeps a label and its field reading as one sentence regardless of their heights. That's what .firstTextBaseline is for, and it's what macOS forms use to line labels up with their fields.

Grid · gridColumnAlignment · gridCellAnchor

Grids: alignment in two dimensions

Grid is the one container where alignment layers: a default for every cell, overridable per column, per row, and per cell — from broadest to most specific:

levelapisets
whole gridGrid(alignment:)default Alignment for every cell
one column.gridColumnAlignment(_:)that column's horizontal guide (declare on any one cell in it)
one rowGridRow(alignment:)that row's vertical guide
one cell.gridCellAnchor(_:)a UnitPoint for this cell — the tool for cells that span columns
 
Grid(alignment: .leadingFirstTextBaseline, horizontalSpacing: 16) {
    GridRow {
        Text("Wi-Fi")
        Text("Connected")
            // the whole values column right-aligns, ledger-style
            .gridColumnAlignment(.trailing)
    }
    GridRow {
        Text("Battery")
        Text("87 %")
    }
}

Note what the column override is: .gridColumnAlignment(.trailing) on one cell re-answers the horizontal question for the entire column — the same publish-a-guide idea as .alignmentGuide, scoped to a column. And .leadingFirstTextBaseline is a composite you've already met: the leading guide horizontally, the first-baseline guide vertically, so labels of different font sizes still sit on a shared baseline per row.

.alignmentGuide(_:computeValue:)

Overriding the answer

.alignmentGuide lets one view give a different answer to the container's question. You name the alignment being asked about, and return a new offset computed from the view's ViewDimensions — which also hands you the view's existing guides, so answers can be relative: d[.top], d[VerticalAlignment.center], d.height. 

HStack(alignment: .center) {
    Image("badge")
        // this view's ".center" is now 10 pt above its real center,
        // so the container pushes the view 10 pt *down* to compensate
        .alignmentGuide(VerticalAlignment.center) { d in
            d[VerticalAlignment.center] - 10
        }
    Text("Neighbors keep their defaults")
}
The classic no-op An override only fires for the alignment the container is actually using. Overriding .leading inside VStack(alignment: .center) changes nothing — nobody asked that question. Match the guide you override to the container's alignment: parameter.

Deliberate overhang

Because a guide may point outside the view's bounds, overrides are also how you hang a badge half off a card's corner — no offset math, and it stays put as either view resizes: 

ZStack(alignment: .topTrailing) {
    CardView()
    BadgeView()
        // the badge's ".top" is its vertical center, and its
        // ".trailing" is its horizontal center → it straddles the corner
        .alignmentGuide(.top)      { d in d.height / 2 }
        .alignmentGuide(.trailing) { d in d.width  / 2 }
}
AlignmentID

Custom guides: aligning across containers

Built-in guides only line up siblings in the same stack. To align views that live in different branches of the hierarchy — say, the values column of two separate rows — define your own alignment. A custom guide propagates upward: a container's answer for it is derived from whichever children explicitly set it, so the outer stack can line up grandchildren. 

extension HorizontalAlignment {
    private struct ValueColumn: AlignmentID {
        static func defaultValue(in d: ViewDimensions) -> CGFloat { d[.leading] }
    }
    static let valueColumn = HorizontalAlignment(ValueColumn.self)
}

VStack(alignment: .valueColumn) {
    HStack { Text("Version");  Text("2.4.1").alignmentGuide(.valueColumn) { $0[.leading] } }
    HStack { Text("Size");     Text("12 MB").alignmentGuide(.valueColumn) { $0[.leading] } }
}

The two value labels line up even though each lives inside its own HStack — the guide value bubbles up through the rows to the outer VStack, which does the aligning. Two things make custom guides tick: the defaultValue is the answer for any view that doesn't set the guide explicitly, and a container adopts the explicit value published by its children — which is what lets a guide cross container boundaries. Give exactly one view per branch the explicit value and the behavior stays predictable.

Icon on the title line

The everyday version of the same trick: an icon next to a title + subtitle block. Center the icon against the whole VStack and it slides downward every time the subtitle wraps to another line. Align it to the title's center instead: 

extension VerticalAlignment {
    private struct TitleCenter: AlignmentID {
        static func defaultValue(in d: ViewDimensions) -> CGFloat {
            d[VerticalAlignment.center]
        }
    }
    static let titleCenter = VerticalAlignment(TitleCenter.self)
}

HStack(alignment: .titleCenter) {
    Image(systemName: "bell.badge")
        .alignmentGuide(.titleCenter) { $0[VerticalAlignment.center] }
    VStack(alignment: .leading) {
        Text("Weekly digest").font(.headline)
            .alignmentGuide(.titleCenter) { $0[VerticalAlignment.center] }
        Text("A summary of everything that happened, however long it wraps.")
            .foregroundStyle(.secondary)
    }
}

A timeline spine

Custom guides scale up: a timeline needs each row's dot centered on the heading of that row's content, while the dots also form one straight vertical spine. The same .titleCenter alignment from above, reused in every row, handles the dot-to-heading match; the dots' fixed width handles the spine — no GeometryReader, no manual offsets: 

ForEach(events) { event in
    HStack(alignment: .titleCenter, spacing: 12) {
        Circle().frame(width: 10, height: 10)
            .alignmentGuide(.titleCenter) { $0[VerticalAlignment.center] }
        VStack(alignment: .leading) {
            Text(event.title).font(.headline)
                .alignmentGuide(.titleCenter) { $0[VerticalAlignment.center] }
            Text(event.details)
        }
    }
}
Anchor<CGRect> · anchorPreference

Anchors: geometry across the whole tree

Guides — even custom ones — coordinate views that share an aligning ancestor. But some layouts need one view to know another view's actual geometry: an underline that slides beneath the selected tab, a connector drawn between two cards. That's the anchor system, and it's genuinely the hardest idea on this page — so let's build it from its two ingredients: why raw coordinates can't work, and what an anchor does about it.

1 · Geometry is meaningless without a coordinate space

“Where is this view?” has no answer by itself — only “where is it as seen from…”. The same box is at one position in the window's coordinates, another in its card's, another in a scroll view's content space (and that one changes every frame while scrolling):

The manual route is GeometryReader with .global or named coordinate spaces — read a frame, store it in @State, use it elsewhere. It works, but you own the bookkeeping: pick the right space, convert between spaces yourself, and accept that measure-into-state triggers another layout pass (hello, stale-frame glitches and update loops).

2 · An anchor is a claim ticket, not a rectangle

An Anchor<CGRect> contains no usable numbers. It's an opaque token meaning “the bounds of that specific view” — with the coordinate-space question deliberately left open. The numbers only materialize when someone resolves the token through a GeometryProxy: 

let rect: CGRect = proxy[anchor]
// “that view's bounds, expressed in MY coordinate space” —
// whoever resolves gets answers relative to themselves.

That deferred resolution is the entire trick. The capturing view doesn't decide the space; the consumer does, implicitly, just by being the one to resolve. No conversions, no named spaces, and it stays correct through scrolling and transforms because resolution happens fresh each layout.

capture (Anchor.Source)token typeresolves to
.boundsAnchor<CGRect>the view's rect, in the resolver's space
.center, .topLeading, .trailing, …Anchor<CGPoint>that point of the view
.rect(…) / .point(…)eithera custom spot in the view's own space

3 · The pipeline: capture, hoist, resolve

Anchors travel through preferences — the system where values flow up the tree, the mirror image of the environment flowing down. Three moves, always the same:

Capture. .anchorPreference(key:value:transform:) takes which geometry to capture (value: .bounds) and a closure that wraps the fresh token into your key's value type. The cryptic-looking { [i: $0] } just means “a one-entry dictionary: my index → my anchor.” Hoist. A PreferenceKey's reduce merges the values from every branch as they bubble upward — for a dictionary, a plain merge. Resolve. An ancestor reads the collected value with .overlayPreferenceValue (or .backgroundPreferenceValue), which hands it the tokens and hosts the view that consumes them; a GeometryReader inside provides the proxy that turns tokens into rects. 

// CAPTURE + HOIST — the key's value is a dictionary of tokens
struct TabAnchors: PreferenceKey {
    static let defaultValue: [Int: Anchor<CGRect>] = [:]
    static func reduce(value: inout [Int: Anchor<CGRect>],
                       nextValue: () -> [Int: Anchor<CGRect>]) {
        value.merge(nextValue()) { $1 }
    }
}

HStack(spacing: 24) {
    ForEach(tabs.indices, id: \.self) { i in
        Text(tabs[i])
            .anchorPreference(key: TabAnchors.self, value: .bounds) { [i: $0] }
            .onTapGesture { withAnimation { selection = i } }
    }
}
// RESOLVE — an ancestor turns the selected tab's token into an underline
.overlayPreferenceValue(TabAnchors.self) { anchors in
    GeometryReader { proxy in
        if let anchor = anchors[selection] {
            Capsule()
                .frame(width: proxy[anchor].width, height: 3)
                .offset(x: proxy[anchor].minX, y: proxy[anchor].maxY + 4)
        }
    }
}

Second example: drawing between views

The tab underline resolves one token. Resolve two and you can draw between views that live in completely different branches — a flow-chart connector, an onboarding arrow pointing at a control. No guide, stack, or frame can express “from the edge of this view to the edge of that one”; two anchors and a Path can: 

// same PreferenceKey shape as TabAnchors, keyed by name
StepCard("Build")
    .anchorPreference(key: CardAnchors.self, value: .bounds) { ["build": $0] }
// …elsewhere, any distance away in the hierarchy…
StepCard("Deploy")
    .anchorPreference(key: CardAnchors.self, value: .bounds) { ["deploy": $0] }

// a shared ancestor connects them — both rects resolve in ITS space,
// so the two points are directly comparable
.overlayPreferenceValue(CardAnchors.self) { anchors in
    GeometryReader { proxy in
        if let from = anchors["build"], let to = anchors["deploy"] {
            Path { p in
                p.move(to: CGPoint(x: proxy[from].maxX, y: proxy[from].midY))
                p.addLine(to: CGPoint(x: proxy[to].minX,  y: proxy[to].midY))
            }
            .stroke(.secondary, style: .init(lineWidth: 1.5, dash: [6, 5]))
        }
    }
    .allowsHitTesting(false)   // the overlay must not eat clicks
}
When to switch systems Reach for guides while views share an aligning parent — cheaper and declarative. Reach for anchors when geometry must cross the tree (indicator under a distant view, lines between views, spotlight cutouts) or when you need the rect itself, not just an offset on one axis. And unlike hand-rolled GeometryReader-into-@State measuring, anchors involve no state round-trip — nothing to go stale, no feedback loops.
matchedGeometryEffect(id:in:)

Matched geometry: alignment over time

Everything so far aligns views that exist at the same moment. matchedGeometryEffect aligns a view with another view across a state change: give both the same id in the same @Namespace, and when one is removed while the other is inserted, SwiftUI interpolates frame and position between them — the “hero” transition where a thumbnail appears to grow into a detail card. 

@Namespace private var hero

if isExpanded {
    CoverDetail()
        .matchedGeometryEffect(id: "cover", in: hero)
} else {
    CoverThumbnail()
        .matchedGeometryEffect(id: "cover", in: hero)
}
// withAnimation(.spring) { isExpanded.toggle() }

Ground rules: exactly one view per id should be the geometry source at any instant (two live sources produce console warnings and jumps — with two simultaneous views, mark one isSource: false); the effect matches geometry, not content, so pair it with a matching visual crossfade; and it works within one window's view tree — for whole-screen transitions on modern OSes, navigationTransition(.zoom) builds on the same idea.

Layout · sizeThatFits · placeSubviews

The Layout protocol: becoming the container

When no stack fits — tags that flow onto new rows, views on a circle — you can be the container. A Layout implements the two sides of the negotiation this page started with: report a size (sizeThatFits), then place each child (placeSubviews). The parent proposes; you dispose.

The conversation

Layout in SwiftUI is a structured dialogue, and writing a Layout means playing the middle role. Your parent proposes a size; you interrogate your subviews with proposals of your own; they answer with sizes; you answer your parent; and once the parent settles your bounds, you place each child.

A ProposedViewSize's dimensions carry three special probes, and subviews answer each differently — Text is the classic responder:

proposalmeansText answers with
nil (.unspecified)“what's your ideal?”one unwrapped line
0 (.zero)“your minimum?”tightest legal size
.infinity“your maximum?”all the room it can use
a number“fit this”wraps into that width

A complete container in twenty lines

Views on a circle — impossible with stacks, and a full, working Layout: 

struct RadialLayout: Layout {
    func sizeThatFits(proposal: ProposedViewSize,
                      subviews: Subviews, cache: inout ()) -> CGSize {
        // take whatever we're offered, resolving nil probes to a default
        proposal.replacingUnspecifiedDimensions()
    }

    func placeSubviews(in bounds: CGRect, proposal: ProposedViewSize,
                       subviews: Subviews, cache: inout ()) {
        let radius = min(bounds.width, bounds.height) / 2 - 20
        let step = 2 * CGFloat.pi / CGFloat(subviews.count)
        for (index, subview) in subviews.enumerated() {
            let angle = step * CGFloat(index) - .pi / 2   // start at 12 o'clock
            subview.place(
                at: CGPoint(x: bounds.midX + cos(angle) * radius,
                             y: bounds.midY + sin(angle) * radius),
                anchor: .center,
                proposal: .unspecified
            )
        }
    }
}

RadialLayout { ForEach(hours) { HourMark($0) } }   // drops in like any stack

Wrapping rows: the flow-layout shape

The other canonical custom layout: tag chips that fill a row and wrap to the next, like text. Unlike the radial layout, here the children's own sizes drive everything — probe each child, pack greedily, wrap on overflow: 

// Sketch — the row-packing helpers (rows(fitting:), rowHeight) are elided.
struct FlowLayout: Layout {
    var spacing: CGFloat = 8

    func sizeThatFits(proposal: ProposedViewSize,
                      subviews: Subviews, cache: inout ()) -> CGSize {
        rows(fitting: proposal.width ?? .infinity, subviews).size   // ① ②
    }

    func placeSubviews(in bounds: CGRect, proposal: ProposedViewSize,
                       subviews: Subviews, cache: inout ()) {
        var origin = bounds.origin                         // ③
        for view in subviews {
            let size = view.sizeThatFits(.unspecified)     // ④
            if origin.x + size.width > bounds.maxX {       // ⑤
                origin.x = bounds.minX
                origin.y += rowHeight + spacing
            }
            view.place(at: origin, proposal: .unspecified)  // ⑥
            origin.x += size.width + spacing
        }
    }
}

FlowLayout { ForEach(tags) { TagChip($0) } }   // drops in like any stack

① proposal.width is the parent's offer, and it's optional — nil is the “what's your ideal size?” probe from the table above. Falling back to .infinity says “unconstrained, I'm a single unwrapped row.”

② The elided rows(fitting:) helper is the real heart of a flow layout: it simulates the packing (measure each chip, start a new row when one won't fit) and reports the total footprint — widest row × summed row heights. The contract that keeps the layout honest: this simulation must reach exactly the same conclusions placeSubviews later acts on, or the container's frame won't match its contents and children draw outside it.

③ bounds is a CGRect, not a size — its origin is not (0,0). The cursor starts at bounds.origin and wraps back to bounds.minX, never to zero; forgetting this is the classic first-custom-layout bug.

④ Each chip is asked its ideal size — for a tag chip, its text plus padding on one line.

⑤ The carriage return: if the chip's right edge would poke past bounds.maxX, reset x to the leading edge and step y down one row.

⑥ place does two jobs: at: origin pins the chip's top-leading corner to the cursor (the default anchor: — the radial layout passed .center instead), and proposal: .unspecified makes the chip render at the same ideal size step ④ measured. Measuring with one proposal and placing with another is the other classic mismatch bug.

One honest simplification in the sketch: the loop steps down by a flat rowHeight, which assumes every chip is the same height — true for tag chips. A general flow layout can't know how far to step down until it has seen the tallest member of the whole row, which is exactly why the real implementation needs the rows(fitting:) pre-pass to group children into rows first — and, since that pre-pass runs in both methods, it's where the cache from the performance note below earns its keep.

Aligning inside your own container

Here's the tie-back to everything above: the guide values this whole page is about are literally your inputs. Each subview hands you a ViewDimensions — the same object an .alignmentGuide closure receives, custom alignments included. So a row that aligns children by baseline, the way HStack(alignment: .firstTextBaseline) does, is a dozen lines — you're implementing the right-hand half of the very first diagram: 

// inside placeSubviews — a single baseline-aligned row
let dims = subviews.map { $0.dimensions(in: .unspecified) }

// the shared line: deepest first-text baseline of any child
let lineY = bounds.minY + (dims.map { $0[.firstTextBaseline] }.max() ?? 0)

var x = bounds.minX
for (subview, d) in zip(subviews, dims) {
    // shift each child so ITS baseline answer lands on the line
    subview.place(at: CGPoint(x: x, y: lineY - d[.firstTextBaseline]),
                  proposal: .unspecified)
    x += d.width + spacing
}

Read it against section one: d[.firstTextBaseline] is each view's answer, lineY is the shared line, and the subtraction is the container shifting each child so the answers meet. That's the entire alignment system, hand-rolled.

Letting children speak: LayoutValueKey

Subviews can carry custom per-child values into your layout — the Layout-world analog of publishing a guide. Declare a LayoutValueKey, let views tag themselves, and read the tag off each subview while placing: 

private struct Flexibility: LayoutValueKey {
    static let defaultValue: CGFloat = 1
}

TagChip(tag)
    .layoutValue(key: Flexibility.self, value: 2)   // I can stretch 2×

// inside the layout:
let weight = subview[Flexibility.self]
Performance note The engine may call sizeThatFits several times per pass (those min/ideal/max probes). If sizing is expensive — the flow layout's row packing, say — compute it once into the cache parameter via makeCache(subviews:) and invalidate in updateCache. Skip it until you measure a problem; () is a fine cache.
And the circle closes A Layout can also publish guides of its own via explicitAlignment(of:in:proposal:subviews:cache:) — deciding what its answer to “where is your .center?” should be, exactly the question the page opened with. Containers all the way down.
case study · the drifting form label

Why the form label drifted

Here's how all of this bites in practice. A macOS Form aligns each row's label with its control using .firstTextBaseline. Swap a row's TextField for a tall TextEditor — for multi-line notes, say — and the label sinks toward the bottom of the row. Recall the table from the top: a view with no text baseline reports its bottom edge. The form dutifully aligned the label's baseline with the bottom of the editor box. 

TextEditor(text: $notes)
    // TextEditor exposes no first-text baseline, so the form's
    // label row has nothing to align the label against and the
    // label drifts. Publish one ≈ where the first line's baseline
    // actually lands (tune the constant by eye for your padding
    // and font).
    .alignmentGuide(.firstTextBaseline) { $0[.top] + 11 }

One line, and it's the whole mental model in miniature: the container asks a question, the default answer is wrong for this view, so the view is taught a better one.
